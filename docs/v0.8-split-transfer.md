# v0.8 - Split-transfer aggregation

**Status:** implemented. Design locked before code.

## 1. Problem

v0.7 finds one on-chain transfer matching the bank amount. The mule
pattern splits a bank deposit across several on-chain legs. v0.7 returns
zero matches. v0.8 aggregates.

## 2. Rules (locked)

1. Static rates by default, --live-rate opt-in.
2. +/-72h window, --window-hours adjustable.
3. Every match is correlation_candidate, tier unverified, note
   "sum matches; split pattern consistent with mule behaviour; not
   proof of same funds".

## 3. Bounds (locked)

- Max 5 legs per candidate.
- Max 50 candidate sets evaluated.
- Min 2 legs (1-leg is correlate()'s job).
- +/-1% tolerance.
- +/-72h window.

If a wallet needs more than 5 legs, Robert does not find it.

## 4. Candidate shape

Normal correlation candidate plus a components list, so a reviewer can
audit the arithmetic.

## 5. What kills a candidate

- Fewer than 2 legs, more than 5 legs.
- Any leg outside the window (whole set discarded).
- Sum outside bank_eur * [0.99, 1.01].
- More than 50 sets evaluated (truncated, audit-logged).

## 6. What Robert still will not do

- Detect mixers or bridges.
- Account for stablecoin depegs.
- Produce a court-admissible conclusion.
- Match across currencies without a rate entry.

## 7. Tests

tests/test_split.py - 6 tests, all passing.

## 8. Known false-negative risk

max_sets=50 stops in itertools.combinations order, not best-first.
v0.9 candidate fix: sort legs by EUR-value proximity before combining.
